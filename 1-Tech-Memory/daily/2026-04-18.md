## 📝 下午补充：QMD embed Bug 记录（15:48）

### 问题描述
`qmd embed` 命令卡在 "Gathering information" 阶段，无法完成 embeddings 生成。

### 根因分析
**node-llama-cpp prebuilt binary 检测逻辑缺陷**：
- 代码根据 `__get_cpu_code_name()` 尝试匹配 `NLC_VARIANT` 来查找预编译 binary
- 但这个函数返回的是 **CPU 特性名**（如 `skylake`），不是 variant 名（如 `haswell`）
- 导致 Variant 匹配永远失败，触发从源码编译 Vulkan backend
- 编译需要 `glslc`（Google Shader Compiler），系统只有 `glslangValidator`
- 最终编译失败或卡死

### 错误日志
```
/bin/glslc: Error: -f: expected hlsl_functionality1 (use -h for usage)
cannot compile mul_mat_vec_iq2_xs_f32_f32_subgroup
```

### 关键代码位置
- 文件：`/usr/lib/node_modules/@node-llama-cpp/nodejs/scripts/get-cpu-code-name.js`
- 函数：`__get_cpu_code_name()` 返回 `skylake` 而非 `haswell`

### 解决方案
1. **临时方案**：使用 `qmd search` 代替 `qmd query`（BM25 全文搜索，不依赖 embeddings）
2. **替代方案**：等待 node-llama-cpp 发布修复版本，或手动 patch CPU variant 检测逻辑

### 经验教训
1. ⚠️ **第三方库检测逻辑可能存在缺陷**，不能假设它正确
2. ⚠️ **预编译 binary 机制有陷阱**：Variant 检测失败会触发源码编译
3. ⚠️ **glslc 和 glslangValidator 不兼容**，不能混用
4. ✅ **QMD search 是可用替代**，BM25 不需要 embeddings
5. ✅ **调查问题要看源码**，而不是只看错误表象
